# Zennly blog template: design proposal (for approval; nothing implemented)

Status: PROPOSAL. No code changed, nothing written to production, no drafts restored, nothing committed or deployed.
Evidence: the live site zennly.io, the connected repo `Zunkireelabs/zennly-marketplace` (read-only), and the real gate run in a real browser on the four existing Zennly drafts.
Mockups: `mockups.html` (and the PNGs in `mockups/`), desktop 1440px and mobile 390px, all rendered through Zennly's own live page and stylesheet.

## 1. What Zennly's blog really is (inspected)

Zennly's repo holds two things: the Next.js marketplace (`src/app`) and an Eleventy marketing workspace (`marketing/`). The 64 published posts live in the second.

| Piece | Where | What it does |
|---|---|---|
| Post source | `marketing/src/blog/<slug>.njk` | Front matter + a plain-HTML body (`<p><strong>`, `<h2>`, `<ul><li>`, `<a>`). No classes, no wrapper. |
| Layout | `marketing/src/_includes/layouts/blog-article.njk` | Builds everything around the body: breadcrumb, H1, subtitle, read-time/dates, cover image, **`<div class="article-body">`** (the body goes here), then Common questions (H2 + H3 per FAQ), Related reading, sidebar CTA + share, Keep reading cards, bottom CTA, footer. |
| Article styling | The site's own stylesheet, scoped to `.article-body` | Styles bare `<h2>`/`<h3>`/`<p>`/`<ul>`. Measured on the real article: **64px above each H2 on desktop, 48px on mobile**. |
| Index | `marketing/src/_data/blogOrder.json` | Ordered list of slugs; position = where the post appears on `/blog/`. **The build fails if a post file is not listed.** |
| Live pages | `src/app/(marketing-light-nav-pink-cta)/businesses/blog/<slug>/page.tsx` + `src/components/marketing/pages/generated/blog-<slug>.ts` | Generated by `scripts/port-businesses-pages.py` from the built mirror (`public/businesses/…`). The repo's build does NOT regenerate them (`prebuild` runs the sync only `--if-missing`). |

So a post goes live only when the `.njk`, the `blogOrder.json` entry and the generated page files all exist.

Headings on the real article are bare (`<h2>`, `<h3>`): the site's stylesheet styles them. That is Zennly's established format. The only classed "subheading" the platform had recorded for Zennly (`v2-mm__aside-title`) is an `<h4>` in the navigation mega-menu panel, not the article (see section 4).

## 2. The template: Zennly's own, not a new design

No new design is created. The template is Zennly's existing `blog-article.njk` layout and `.article-body` styling. What the platform needs is a **generation contract** for Zennly's blog target, derived from Zennly's own 64 posts:

- Target: `marketing/src/blog/<slug>.njk` (replaces the stale `docs/marketing` target left from before the repo was connected). Extension `.njk`, `layout: layouts/blog-article.njk`.
- Body: **HTML only** (a `.njk` file does not render markdown): `<p>`, `<h2>`, `<h3>`, `<ul>/<ol><li>`, `<strong>`, `<a href>`. No classes, no wrapper, no H1 (the layout supplies the title), H2 then H3 with no skipped level.
- Nothing else about the look is decided by the generator: spacing, typefaces, colours and responsive behaviour come from Zennly's layout and stylesheet, exactly as for the 64 existing posts.

## 3. `marketing/src/blog/<slug>.njk` and how it is connected

Front matter is derived at generation time from the keys every one of the 64 sibling posts declares (the platform's existing sibling-contract reader), never hard-coded. Sketch of the mapping:

| Front matter | Source |
|---|---|
| `layout`, `ogType`, `bodyClass` | constants shared by every sibling (`layouts/blog-article.njk`, `article`, `page--light-nav page--pink-cta`) |
| `title`, `h1`, `metaDescription` | the draft's title and meta description (siblings carry the `# SEOAI:` markers; kept) |
| `datePublished`, `dateModified` | the publish date |
| `category`, `categoryAnchor` | one of Zennly's **existing** categories (never a new one; if none fits, flagged for review) |
| `readTime` | computed from the word count, in Zennly's "5 min read" form |
| `subtitle`, `cardExcerpt` | the draft's quick answer / meta description |
| `faq[]` | the draft's FAQ items (the layout renders "Common questions") |
| `relatedReading[]` | only links to pages that exist on zennly.io |
| `coverImage`, `coverAlt` | **needs your decision** (below): an existing Zennly image, never another client's |
| sidebar/bottom CTA headings and bodies | **needs your decision** (below) |

Body: the quick answer as the bold opening paragraph (as in Zennly's own posts), then `<h2>` sections.

Connection points, in one PR:
1. `marketing/src/blog/<slug>.njk` (new).
2. `marketing/src/_data/blogOrder.json`: slug added at the position it should take on `/blog/` (a person or the owner's rule decides; today's first entry is the most recent post). Without it the Eleventy build fails.
3. The three generated page files (`page.tsx`, `generated/blog-<slug>.ts`, `src/lib/businesses-ported.ts`) from the repo's own sync + port scripts.

Step 3 needs the repo's toolchain (Eleventy build + a Python script), which the platform cannot run. Options:

| Option | What | Autonomous? | Notes |
|---|---|---|---|
| **A** | A person runs `npm run sync:businesses` then `python3 scripts/port-businesses-pages.py blog/<slug>` on the PR branch and pushes | No | Least change. Fine for the first articles. |
| **B (recommended)** | One-time change to Zennly's repo CI: on a PR touching `marketing/src/blog/**`, run the build + sync + port and commit the generated files to the PR branch | Yes | Uses the client's own scripts; the build also catches `blogOrder.json` drift. Needs your approval to add the workflow. |
| C | The platform writes the generated files itself, copying the converter's logic | Yes | Not recommended: it duplicates a converter that can change, and a mistake ships a broken live page. |

## 4. The mega-menu heading-class capture bug, and the fix

Why it happened (verified in the code):
- `segment.js` `textHierarchyOf` treats the heading of every content-role block as a "subheading", including the mega-menu panel, because block roles are positional (first = hero, last = footer) and nothing marks a menu as chrome.
- `profile-extract.js` `subheadingSamplesByPageType` keeps only headings that **carry a class**. Zennly's real article headings are bare, so they never counted; the only classed non-H1 heading on the page was the menu's `<h4 class="v2-mm__aside-title">`.
- `correctPageTypeTextHierarchy` then confirmed that class as "observed".

Proposed fix, so it cannot recur:
1. **Element-level chrome exclusion at capture.** Record each heading's ancestors; a heading inside `nav`, `header`, `footer`, `aside`, a dialog, `[role=navigation]`, `[aria-hidden]` or a menu/mega-menu container is never evidence.
2. **Body region only.** Article subheading evidence is read only from `h2`/`h3` inside the same body region the render gate measures.
3. **Bare is evidence, not absence.** Record `{ role: 'subheading', classes: null, bare: true, observed: n }` when the body headings carry no class, and never replace it with a class from elsewhere. Bare means "the layout styles them".
4. **Consumer validation.** The article heading standard accepts a class only if it was observed on a body heading; otherwise it is treated as layout/inherit, and the render gate (which measures the real article) decides.
5. **Self-repair detector** `heading-evidence-not-in-body`: flags any recorded subheading class that no heading in the reference article's body uses.
6. **Tests:** a fixture of Zennly's real article markup (menu `<h4>` plus bare `<h2>`) must produce a bare finding and never `v2-mm__aside-title`; the same fixture per existing client must not change its result.

Zennly's profile would then be re-derived (a production step, needing your approval).

## 6. The four existing Zennly articles

They are re-rendered, not rewritten: their stored content (title, quick answer, sections, FAQ) goes through the proposed contract. Result of the unchanged real gate, in a real browser, with the proposed rendering:

| Draft | Topic | Real gate (desktop + mobile) |
|---|---|---|
| 3820 | benefits of salon management software | matches |
| 3821 | how a salon management system improves operations | matches |
| 3837 | benefits of salon management software (same topic as 3820) | matches |
| 3838 | can software help with appointment scheduling | matches |

The gate now also checks colour, typeface, heading weight and heading spacing, not only sizes. Today's rendering fails it (64px expected above each H2, 0 produced); the proposed rendering passes it. The structure guard (H2/H3 only, no H1 in the body, no skipped level) is clean.

Before they could ship, things only a person can settle:
- **3820 and 3837 are the same article twice.** Ship one.
- **Customer stories.** The articles cite specific customers (e.g. a sauna company in Oregon, a studio in Portland). These must be verified with Zennly or removed before publishing.
- **Cover image and category** for each article (existing Zennly assets and categories only).
- **Sidebar and bottom CTA wording** (reuse the wording of existing posts in the same category, or approve new copy).

Flow once approved and deployed: restore the four from abandoned to draft through the re-render path (production step, your approval), you review them in the dashboard, then a PR with the five files (option B) is opened for you to merge.
